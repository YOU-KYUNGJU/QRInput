# FITI QR 입고 자동화 통합 개발 계획서 초안

- 작성일: 2026-04-11
- 대상 시스템: FITI시험연구원 시험관리시스템 QR 입고 자동화
- 대상 팀:
  - 분석화학평가팀
  - 가공성능평가팀

## 1. 프로젝트 배경

현재 각 팀은 별도의 AutoHotkey 스크립트로 FITI 시험관리시스템의 QR 입고 처리를 자동화하고 있다.

운영 방식:

1. 작업 스케줄러가 하루 3회 실행된다.
2. 각 팀 스크립트가 FITI 시험관리시스템에 팀별 아이디/비밀번호로 로그인한다.
3. 상단의 QR 아이콘을 클릭해 QR스캔 창을 연다.
4. CSV 파일의 접수번호를 QR스캔 창으로 전송한다.
5. 빨간색 체크 박스가 체크되지 않은 경우 체크한다.
6. 저장 후 다음 접수번호를 반복 처리한다.

현재 문제는 크게 두 가지다.

1. 팀별로 거의 같은 코드가 복제되어 유지보수 비용이 높다.
2. 하루 3회 배치 실행 구조라 CSV가 생성된 뒤 실제 처리까지 대기 시간이 길다.

구성:

1. `QRinput_main.ahk`
2. `config_analysis.ini`
3. `config_processing.ini`

실행 흐름:

2. 각 팀 설정별로 순차 실행
3. 한 팀 처리 완료 후 로그아웃 또는 프로세스 재기동
4. 다음 팀 처리 진행

장점:

- 가장 현실적이고 기존 코드 재사용이 쉽다.
- 두 팀의 공통 로직을 한 번만 개선하면 된다.

주의:

- FITI가 동시 다중 로그인에 약하면 반드시 팀별 순차 처리로 설계해야 한다.

### 방식 B: 팀별 런처는 유지하고 공통 라이브러리만 공유

구성:

1. `QRinput_analysis.ahk`
2. `QRinput_processing.ahk`
3. `QRinput_common.ahk`

장점:

- 운영 변경 저항이 적다.
- 기존 팀별 진입점은 유지하면서 내부 엔진만 공통화 가능하다.

단점:

- 완전 통합은 아니고 반통합 구조다.

현 단계 권장:

- 1차는 방식 B로 안정화
- 2차에 방식 A로 통합

이유:

- 현재 두 팀의 실패 정책과 CSV 규칙이 조금 달라서 바로 완전 통합하면 운영 리스크가 커질 수 있다.

## 5-1. 접수번호 추출 방식

두 팀의 CSV 구조 차이를 고려해 접수번호 추출 방식은 둘 다 지원하는 것이 맞다.

지원 방식:

1. 조합형
2. 완성형

조합형:

- A열, B열, D열 등 필요한 열을 조합해 `@...@` 형태 접수번호 생성

완성형:

- CSV 셀 안에 이미 완성된 13자리 또는 최종 접수번호가 있으면 그 값을 우선 사용

권장 규칙:

1. 팀 설정에 기본 추출 방식을 명시
2. 기본 방식으로 값이 없으면 보조 방식 자동 시도
3. 둘 다 실패하면 해당 행을 실패 로그에 남기고 다음 행으로 진행

즉, 엔진은 `추출 전략 2종 지원 + 팀별 기본값 선택` 구조가 적절하다.

샘플 기준 확정 규칙:

분석화학평가팀 CSV 샘플:

- 샘플 파일: `H1.csv`, `H2.csv`
- 구조: `A열=접수번호 앞부분`, `B열=일련번호`, `C열=시료번호`, `D열=연도코드`
- 생성 규칙: `@ + A열 + D열 + B열 + @`
- 예:
  - `H231,14717,1,26` -> `@H2312614717@`
  - `H355,00476,1,26` -> `@H3552600476@`

가공성능평가팀 CSV 샘플:

- 샘플 파일: `20260410_095128.csv`, `20260410_095205.csv`
- 구조: `B열에 완성된 접수번호 저장`
- 사용 규칙: B열 값을 그대로 사용
- 실제 운영에서는 `B1`만이 아니라 `B2`, `B3` 등 여러 행이 채워질 수 있음
- 예:
  - `@W2412600042@`
  - `@W2412600043@`

구현 권장 우선순위:

1. 값이 이미 `@...@` 형태면 그대로 사용
2. 아니면 팀 설정 기준으로 조합 생성
3. 생성 후 정규식 검증 실패 시 로그 남기고 다음 행 진행

가공성능평가팀 구현 주의:

1. `B1 단건 처리`로 고정하면 안 됨
2. `B열 전체`를 스캔하면서 `@...@` 형식의 유효값만 처리 대상으로 선별해야 함
3. 헤더, 안내문구, 예시 문자열, 빈값은 자동 제외해야 함

## 6. 스케줄 개선안

현재:

- 오전 1회
- 점심 1회
- 저녁 1회

현재 작업 스케줄러 확인 결과:

1. `QR입고` 작업 존재
2. 일일 트리거 시각은 `06:55`, `11:55`, `19:24`
3. 별도 `QR입고 닫기` 작업도 운영 중인 것으로 보임

문제:

- CSV 생성 후 실제 반영까지 수 시간 지연 가능
- 긴급 접수나 당일 처리 대응이 느림

### 개선안 1: 작업 스케줄러 10분 주기 실행

권장도: 높음

특징:

1. 현재 배치 구조를 유지할 수 있다.
2. 운영 난도가 낮다.
3. 장애 발생 시 프로세스가 다음 주기에 복구될 여지가 있다.

필수 조건:

1. 이미 처리한 CSV 재처리 방지
2. 실행 중 중복 실행 방지
3. 실패 파일과 성공 파일 구분 저장

### 개선안 2: 작업 스케줄러 5분 주기 실행

권장도: 중간

특징:

1. 더 빠르지만 중복 실행과 파일 잠금 관리가 더 중요하다.
2. FITI 응답이 느릴 때 다음 실행과 겹칠 위험이 있다.

적용 조건:

1. 10분 주기에서 안정성 확인 후 전환
2. 단일 실행 락 파일 또는 실행 PID 체크 필수

### 개선안 3: 상시 실행형 감시 프로그램

권장도: 중장기

특징:

1. 지정 시간 동안 항상 실행
2. 1~2분 간격으로 폴더를 감시하거나 새 파일 발생 시 즉시 처리

장점:

- 가장 빠르다.

단점:

- 운영 복잡도가 높다.
- FITI 세션 유지, 메모리 누수, 장시간 예외 처리까지 설계해야 한다.

### 스케줄 1차 권장안

1차 운영 권장안은 `작업 스케줄러 10분 주기 실행`이다.

권장 예:

1. 평일 08:00-18:30 구간 10분마다 실행
2. 점심시간도 동일 주기 유지
3. 야간 처리 필요 시 19:00-21:00 구간은 20분마다 실행

이 방식은 현재 배치형 구조를 크게 바꾸지 않으면서도 처리 대기 시간을 실질적으로 줄일 수 있다.

목표 반영 시간:

- CSV 생성 후 `1시간 이내 반영`

위 목표 기준으로도 현재 1일 3회 방식보다 촘촘한 실행 주기로 바꾸는 것이 필요하다.

## 6-1. FITI 세션 운영 정책

시험관리시스템은 자정에도 자동 연결이 끊길 수 있고, 낮에도 세션이 끊길 수 있으므로 장시간 로그인 유지에 의존하면 안 된다.

권장 정책:

1. 실행 시작 전에 기존에 열려 있는 FITI 프로세스 또는 관련 창이 있으면 먼저 종료
2. 실행 주기마다 FITI를 새로 실행
3. 로그인 확인 후 작업 수행
4. 작업 완료 후 FITI 종료
5. 작업 중 세션 끊김 감지 시 자동 재로그인
6. 자동 재로그인은 최대 3회까지 시도
7. 3회 실패 시 실패 로그를 남기고 다음 스케줄 실행 시간까지 대기

이유:

1. 끊어진 세션을 계속 끌고 가는 것보다 재기동이 안정적이다.
2. 메모리 누수나 UI 꼬임이 누적되는 것을 줄일 수 있다.
3. 자정 세션 만료 대응이 쉬워진다.

## 7-1. 실패 처리 정책

요구사항 기준으로 QR 스캔 실패 시 시스템은 멈추지 않고 다음 작업으로 넘어가야 한다.

정책:

1. 행 단위 실패는 `실패 로그`에 남기고 다음 행 진행
2. 파일 단위 실패는 해당 파일 상태를 `partial` 또는 `failed`로 남기고 다음 파일 진행
3. 동일 행은 최대 3회까지 재시도
4. 3회 실패 시 실패 로그를 남기고 다음 행으로 진행
5. 팀 단위 재로그인이 필요한 오류는 최대 3회 자동 재로그인 후 다음 스케줄까지 대기
6. 실패한 건은 다음 실행 때 다시 재시도
7. 전체 프로그램은 치명적 예외가 아닌 이상 종료하지 않음

예외 분류:

1. 데이터 오류: 접수번호 조합 실패, 빈값
2. 화면 오류: QR 창 미존재, 버튼 미검출
3. 세션 오류: 로그인 끊김, 메인 창 이탈
4. 저장 오류: 체크 실패, 저장 실패

각 예외는 `팀명`, `파일명`, `행번호`, `접수번호`, `오류코드`, `시각`과 함께 기록해야 한다.

## 8-1. 성공/실패 로그 설계

성공한 접수번호도 기존처럼 그림 파일과 함께 로그를 남기는 것이 좋다.

권장 형식은 `CSV`다.

추천 이유:

1. 나중에 필터, 집계, 검색이 쉽다.
2. 성공/실패/재시도 횟수 분석이 가능하다.
3. 팀별 처리량과 실패율을 엑셀로 바로 확인할 수 있다.
4. txt보다 구조화가 쉬워 추후 대시보드나 보고서로 연결하기 좋다.

권장 구성:

1. 메인 로그는 `CSV`
2. 사람이 빠르게 읽는 요약 로그가 필요하면 보조로 `txt`

즉, 기본은 `CSV`, 선택적으로 `txt summary`를 추가하는 방식이 좋다.

권장 CSV 컬럼:

1. run_id
2. team
3. process_date
4. source_file
5. row_no
6. receipt_no
7. status
8. reason
9. retry_count
10. screenshot_path
11. started_at
12. finished_at
13. elapsed_ms
14. fiti_login_retry
15. row_retry_count

상태값 예:

1. success
2. failed
3. skipped
4. retried
5. session_relogin
6. wait_next_schedule

스크린샷 정책:

1. 성공 건 스크린샷은 전체 저장
2. 실패 건 스크린샷도 전체 저장
3. 로그는 성공/실패 모두 남김

## 10. 기대 효과

1. 코드 중복 제거로 유지보수 시간 감소
2. 팀 추가 시 설정 파일만 추가하면 확장 가능
3. CSV 생성 후 FITI 반영까지의 대기 시간을 1시간 이내 목표로 단축
4. 장애 원인 분석이 쉬워짐
5. 팀별 운영 정책은 유지하면서 핵심 엔진은 표준화 가능

## 11. 현재 기준 권장 의사결정

지금 바로 가장 현실적인 방향은 다음과 같다.

1. 두 시스템을 완전히 새로 만들지 말고 공통 함수 중심으로 먼저 묶는다.
2. 작업 스케줄러는 하루 3회에서 `1시간 이내 반영이 가능한 주기`로 먼저 바꾼다.
3. 초기 권장값은 `30분 주기`, 안정화 후 `10분 주기` 검토
4. 그 전에 `중복 실행 방지`, `성공/실패 이력 로그`, `재시도 제한`, `기존 FITI 종료`를 먼저 넣는다.
5. 안정화 후 `10분 주기` 또는 상시 감시형으로 확장한다.

즉, 통합과 속도 개선은 동시에 가능하지만, 순서는 `공통화 -> 안전장치 -> 실행 주기 단축`이 맞다.

## 11-1. QRinput 시스템 실행 모델 권장안

`FITI는 작업 후 종료`, `QRinput은 오래 살아있을지 여부`는 분리해서 판단하는 것이 맞다.

권장안:

1. FITI시험관리시스템은 매 실행 종료
2. QRinput은 1차 단계에서는 상시 미종료형보다 `주기 실행형`이 더 적절

이유:

1. FITI 세션이 낮과 밤에 끊기므로 FITI는 짧게 쓰고 닫는 편이 안정적이다.
2. QRinput까지 상시 띄워두면 예외 누적, 메모리 누수, 화면 꼬임 대응이 어려워진다.
3. 작업 스케줄러 10분 주기 실행이면 사실상 상시 운영과 비슷한 체감 속도를 낼 수 있다.

중장기 대안:

- 나중에 충분히 안정화되면 `QRinput supervisor`를 상시 실행시키고, 내부에서 주기적으로 FITI만 띄워 처리하는 구조는 가능하다.

하지만 1차 구축은 `짧게 실행되고 종료되는 QRinput worker`가 더 안전하다.

## 12. 추가 확인 필요 사항

1. 두 팀을 한 번 실행할 때 같은 FITI 프로세스에서 계정 전환이 가능한지
2. 두 팀 모두 CSV 포맷이 완전히 같은지
3. 빨간 체크 박스 판정이 정확히 같은 좌표/같은 컨트롤인지
4. 저장 완료 판정 기준이 두 팀 모두 같은지
5. 오전/저녁 날짜 판정 규칙이 운영상 꼭 필요한지
6. 원하는 목표 반영 시간

현재 자료 기준으로는 `CSV 생성 후 1시간 이내 반영`을 1차 운영 목표로 두는 것이 맞다.

추가 확보된 정보:

1. QR스캔 창의 빨간 체크 박스 체크 상태 화면 확보
2. Window Spy 기준 체크 영역 근처 픽셀 색상은 `FF0000`
3. 현재 운영 스크립트처럼 `PixelGetColor` 기반 판정이 가능함
4. 체크 박스는 `QR스캔` 창 내 우측 `입고` 컬럼 영역에 위치
5. QR스캔 창의 빨간 체크 박스 미체크 상태 화면 확보
6. 미체크 상태에서는 같은 위치에 빨간 표시가 없음
7. 저장 완료 시점에는 별도 특이 팝업이나 독립 화면이 없다고 봐야 함
8. 가공성능평가팀 CSV는 여러 B행이 채워질 수 있음
9. 세션 끊김 또는 로그인 풀림 화면은 아직 미확보

현 단계 권장:

1. 1차 구현은 `PixelGetColor` 기반 유지
2. 가능하면 보조로 컨트롤 좌표 또는 클릭 좌표를 설정값으로 분리
3. `체크 전/후` 픽셀 기준을 함께 설정값으로 관리
4. 저장 완료 판정은 별도 팝업 검출보다 저장 흐름 후 화면 상태 변화 기준으로 구현

## 13. 미처리 건 재개 방식

`입고 처리 후 시간이 지나고 입고 안 된 것부터 어떻게 이어서 진행할지`는 처리 이력과 원본 파일 상태를 같이 봐야 한다.

권장 방식:

1. 실행할 때마다 대상 폴더를 다시 스캔
2. CSV 각 행마다 고유 키를 생성
3. 성공 이력에 있는 키는 건너뜀
4. 성공 이력이 없는 행만 처리
5. 실패 이력이 있어도 성공 이력이 없으면 재시도 대상으로 포함

고유 키 예:

`team + source_file + row_no + receipt_no`

또는 receipt 번호가 완전히 유일하면:

`team + receipt_no`

파일 단위 후처리:

1. 파일 내 모든 행 성공 시에도 원본 CSV는 그대로 유지
2. 일부 실패가 남아 있으면 역시 원본 위치 유지
3. 다음 실행 시 아직 성공 기록이 없는 행만 다시 시도

가공성능평가팀 적용 시:

1. 하나의 CSV에 여러 접수번호 행이 존재할 수 있으므로 행 단위 처리 이력이 반드시 필요
2. 고유 키는 `team + source_file + row_no + receipt_no` 구조를 우선 사용

이 구조면 시스템은 "마지막으로 어디까지 했는지"를 메모리에 들고 있을 필요가 없다.

매 실행마다:

1. 폴더를 본다.
2. 로그를 본다.
3. 아직 성공하지 않은 건만 처리한다.

즉, 재개 기준은 `현재 CSV 상태 + 처리이력 CSV` 조합으로 관리하는 것이 가장 안정적이다.
